# 文字起こしエンジン実測レポート（Phase F-2）

`transcribe.whisper.engine` で選べる 3 エンジンのうち、**faster（whisper-ctranslate2）** と
**cpp（whisper.cpp / whisper-cli）** を実際の会議録音で比較した記録。

目的は「**利用側に Python を入れさせずに**（= cpp エンジンで）、今と同じ品質と速度が出るか」の判断。
Mac / Ubuntu で同じ計測をするときの比較基準にもなるよう、環境と手順を残す。

- 計測日: 2026-08-15
- 結論: **速度・品質とも faster と cpp はほぼ互角**。ただし cpp は `-mc 0`（`max-context=0`）が必須。
  素の既定のままでは幻覚ループで品質が大きく崩れる。

## 2. 実行条件をどう揃えたか

エンジン間でサンプリング条件が違うと比較にならないため、先に既定値を突き合わせた。

| パラメータ | faster（whisper-ctranslate2） | cpp（whisper-cli） | 揃っているか |
| --- | --- | --- | --- |
| beam_size | 5 | 5（`-bs`） | ○ |
| best_of | 5 | 5（`-bo`） | ○ |
| temperature | 0（fallback あり） | 0（`-tp` / fallback あり） | ○ |
| 直前テキストの引き継ぎ | `condition_on_previous_text=True` | `-mc -1`（無制限） | ○（既定は同じ思想） |
| **繰り返し検出** | **`compression_ratio_threshold=2.4`** | **相当機能なし** | **×（これが差の主因）** |

whisper-cli の実行ログにも `5 beams + best of 5` と出るため、グリーディではなくビームサーチで動いている。
**決定的な違いは、faster にある「繰り返しを検出して再生成する」仕組みが whisper.cpp に無いこと。**

公平を期すため、各エンジンとも**まっさらな出力フォルダから**実行した（分割・文字起こしとも全て新規）。

```powershell
# faster（既定）
java "-Dspring.shell.interactive.enabled=false" `
  -jar target\transcribe-shell-0.0.1-SNAPSHOT.jar `
  transcribe "C:\Users\<ユーザー>\Music\sample-a.MP3" -m small -o <出力先>

# cpp
java "-Dspring.shell.interactive.enabled=false" `
  "-Dtranscribe.whisper.engine=cpp" `
  "-Dtranscribe.whisper.cpp.command=C:\tools\whisper.cpp\Release\whisper-cli.exe" `
  -jar target\transcribe-shell-0.0.1-SNAPSHOT.jar `
  transcribe "C:\Users\<ユーザー>\Music\sample-a.MP3" -m small -o <出力先>
```

## 3. 速度

| エンジン | 合計（アプリのログ） | 壁時計 | part ごと |
| --- | --- | --- | --- |
| **faster (int8)** | **13分7秒** | 789秒 | 2:22 / 3:59 / 3:31 / 3:15 |
| **cpp（`-mc 0`・現在の既定）** | 13分37秒 | 819秒 | 3:27 / 4:02 / 4:10 / 1:58 |
| cpp（whisper-cli の素の既定） | 15分2秒 | 904秒 | 5:00 / 4:04 / 4:39 / 1:18 |
| openai | 未計測 | — | 参考のため実行したが中断 |

- 34.5分の音声を 13分前後で処理（**約 2.6 倍速**）。
- **cpp は `-mc 0` を足した方が全体では速い**（15分2秒 → 13分37秒）。幻覚ループは無駄なトークン生成なので、
  直すと速度も改善する。
- ただし part_003 だけは遅くなった（1分18秒 → 1分58秒）。これは素の既定が「(音楽)」を吐いて
  **早々に処理を打ち切っていた**ためで、速さと引き換えに中身が無かった（下記）。

## 4. 精度（幻覚ループの量）

### 指標について

行単位の重複率だけでは、**1行の中で同じ表現が繰り返される**ケースを見逃す（cpp は1行が長い）。
そこで gzip 圧縮比を主指標にした。これは whisper 自身が繰り返し検出に使う
`compression_ratio_threshold` と同じ考え方で、**同じ表現の反復が多いほど圧縮比が高くなる**。

日本語の自然な会話文はおおむね 2.5〜3.5 に収まる。

### 結果

| 指標 | faster (int8) | cpp（`-mc 0`） | cpp（素の既定） |
| --- | --- | --- | --- |
| 文字数 | 10,982 | 11,198 | 12,192 |
| 行数 | 754 | 426 | 591 |
| **gzip 圧縮比**（低いほど自然） | **3.18** | **3.21** | **4.54** |
| 行内の繰り返し | 0 行 | 1 行（172文字 = 全体の 1.5%） | 1 行 |
| 行単位の重複率 | 6.9% | 6.1% | 38.1% |
| 最多の重複行 | 「はい。」14回（自然な相槌） | 「クリームチョコレートを使用されています。」9回 | 「(小麦粉を少しずつ入れてください。)」**208回** |

**`-mc 0` によって cpp は faster と同等（3.21 対 3.18）になった。**
素の既定（4.54）は、文字数だけ多くて中身が繰り返しで水増しされている状態。

### part ごとの出力サイズ（バイト）

| | part_000 | part_001 | part_002 | part_003 |
| --- | --- | --- | --- | --- |
| faster | 3,202 | 10,089 | 10,504 | 5,643 |
| cpp（`-mc 0`） | 4,749 | 10,730 | 10,721 | 5,039 |
| cpp（素の既定） | 12,188 | 10,199 | 10,095 | **403** |

素の既定は part_003 が **403 バイト**しかない（≒ 4.5分ぶんをほぼ取りこぼした）。
一方 part_000 は 12,188 バイトと多いが、これは繰り返しによる水増し。

### 実際の出力

**part_003（270秒）— 素の既定は崩壊、`-mc 0` で回復**

```
[faster ]  ま、さっき取り返されていたんですけど、/ ドッグは5御休なのです。/
           どうこまれてきるかというのがあると思います。/ ...（5,643 バイト）

[cpp -mc0] ずっと、他の、まあさっき振り返されてたんですけど、他559なので、
           どこまでできるかっていうのが、今、そこは、あります。/ そうですね。/ ...（5,039 バイト）

[cpp 既定 ] ずっと、他の、まあさっき振り返されてたんですけど... /
           (音楽) / (音楽) / (音楽) / (音楽) ...（403 バイト）
```

**part_000 冒頭 — cpp は `-mc 0` でも1箇所だけループが残る**

```
[faster ]  【音楽】/ 優先でやるのもかりかなと思ってます / アプリプス? /
           アプリプステレガーとみんなで始まるので / っていうぐらいかなと思ってますが / ...

[cpp -mc0] [音楽] / (中村)優先でやるのも仮かなと思ってます / (大平)うん / (大平)アフェプト? /
           (中村)アフェプトでやるのも アフェプトでやるのも アフェプトでやるのも ...（172文字ループ）
```

### エンジンごとの傾向

- **faster**: 繰り返しゼロ。句読点は少なめで、短い行に分かれる（754行）。
- **cpp**: 句読点が丁寧に付き、1行が長い（426行）。ただし
  - `(中村)` `(大平)` のような**話者ラベルを勝手に付ける**ことがある（話者分離は無効なのでモデルの推測）。
  - `クリームチョコレートを使用されています。` のような**文脈外の語**を混ぜることがある。
  - 冒頭など一部でループが残る（全体の 1.5%）。

どちらも固有名詞・専門用語の誤変換は同程度に発生する（`small` モデルの限界）。

## 5. チューニングの経緯（1変数ずつ検証）

崩れが最も激しかった part_003（270秒）で、パラメータを1つずつ足して効果を測った。

| 段階 | 重複率 | 所要時間 | 出力 | 判断 |
| --- | --- | --- | --- | --- |
| ベースライン（素の既定） | 78.9% | 79.6秒 | 403 バイト | 「(音楽)」16回連続で実質崩壊 |
| **(1) `-mc 0` を追加** | **4.1%** | 117.2秒 | **5,039 バイト**（12.5倍） | **十分改善。これを採用** |
| (2) `--suppress-nst` を追加 | 未実施 | — | — | (1) で足りたため不要 |
| (3) VAD を有効化 | 未実施 | — | — | 同上（VAD モデルの別途入手も不要） |

`-mc 0` は「直前のテキストを文脈として引き継がない」設定。whisper.cpp には faster のような
繰り返し検出が無いため、**文脈の引き継ぎを切ることが実質的な対策**になる。

## 6. 結論と、実装への反映

### 判断

- **Windows は faster(int8) を継続**。速度・品質とも僅差で勝り、幻覚もゼロだった。
- **Mac / Ubuntu は cpp で実用水準**。Python 不要という当初の目的を、品質をほぼ落とさずに達成できる。
- **cpp を使うなら `-mc 0` は必須**。素の既定では「同じ文が208回」レベルで崩れ、要約にも使えない。

### この計測を受けて入れた変更

| 変更 | 内容 |
| --- | --- |
| `transcribe.whisper.cpp.max-context` | **既定 0**（`-mc 0` を渡す）。負値なら `-mc` を渡さず whisper-cli の既定に任せる |
| README | 「どのエンジンを選ぶか（実測）」の比較表と `max-context` の説明を追記 |

### 未計測・今後

- **openai エンジン**: 参考のため実行したが、所要時間が長い（30〜60分見込み）ため中断した。
- **cpp に残る 1.5% のループ**: `--suppress-nst` や VAD で消せる可能性がある。実運用で気になったら試す。
- **量子化モデル**: `--model small-q5_1`（181MB）で速度・品質がどう変わるか。モデル置き場に
  `ggml-small-q5_1.bin` を置けば設定変更なしで比較できる。
- **Mac（Intel）での再計測**: 本レポートと同じ手順で計測すれば、そのまま比較できる。
  Metal が効かないため、Windows と同程度かやや遅い想定。

## 7. 計測の再現方法

```powershell
# 1. 出力フォルダを分けて（または --force を付けて）各エンジンを実行する
#    ※冪等性があるため、同じフォルダに再実行するとスキップされて計測にならない

# 2. 所要時間はアプリのログに出る
#    [4/4] 文字起こし完了: 4件 / 合計 13分37秒 (engine=cpp, model=small)

# 3. 圧縮比（幻覚の量）は _all.txt から算出する
$bytes = [System.IO.File]::ReadAllBytes("<出力先>\sample-a_all.txt")
$ms = New-Object System.IO.MemoryStream
$gz = New-Object System.IO.Compression.GZipStream($ms, [System.IO.Compression.CompressionLevel]::Optimal)
$gz.Write($bytes, 0, $bytes.Length); $gz.Close()
"圧縮比: {0}" -f [math]::Round($bytes.Length / $ms.ToArray().Length, 2)
```
