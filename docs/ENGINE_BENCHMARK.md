# 文字起こしエンジン実測レポート（Phase F-2）

`transcribe.whisper.engine` で選べる 3 エンジンのうち、**faster（whisper-ctranslate2）** と
**cpp（whisper.cpp / whisper-cli）** を実際の会議録音で比較した記録。

目的は「**利用側に Python を入れさせずに**（= cpp エンジンで）、今と同じ品質と速度が出るか」の判断。
Mac / Ubuntu で同じ計測をするときの比較基準にもなるよう、環境と手順を残す。

- 計測日: 2026-08-15
- 結論: **速度・品質とも faster と cpp はほぼ互角**。ただし cpp は `-mc 0`（`max-context=0`）が必須。
  素の既定のままでは幻覚ループで品質が大きく崩れる。

## 2. 実行条件をどう揃えたか

エンジン間でサンプリング条件が違うと比較にならないため、先に既定値を突き合わせた。

| パラメータ | faster（whisper-ctranslate2） | cpp（whisper-cli） | 揃っているか |
| --- | --- | --- | --- |
| beam_size | 5 | 5（`-bs`） | ○ |
| best_of | 5 | 5（`-bo`） | ○ |
| temperature | 0（fallback あり） | 0（`-tp` / fallback あり） | ○ |
| 直前テキストの引き継ぎ | `condition_on_previous_text=True` | `-mc -1`（無制限） | ○（既定は同じ思想） |
| **繰り返し検出** | **`compression_ratio_threshold=2.4`** | **相当機能なし** | **×（これが差の主因）** |

whisper-cli の実行ログにも `5 beams + best of 5` と出るため、グリーディではなくビームサーチで動いている。
**決定的な違いは、faster にある「繰り返しを検出して再生成する」仕組みが whisper.cpp に無いこと。**

公平を期すため、各エンジンとも**まっさらな出力フォルダから**実行した（分割・文字起こしとも全て新規）。

```powershell
# faster（既定）
java "-Dspring.shell.interactive.enabled=false" `
  -jar target\transcribe-shell-0.0.1-SNAPSHOT.jar `
  transcribe "C:\Users\<ユーザー>\Music\sample-a.MP3" -m small -o <出力先>

# cpp
java "-Dspring.shell.interactive.enabled=false" `
  "-Dtranscribe.whisper.engine=cpp" `
  "-Dtranscribe.whisper.cpp.command=C:\tools\whisper.cpp\Release\whisper-cli.exe" `
  -jar target\transcribe-shell-0.0.1-SNAPSHOT.jar `
  transcribe "C:\Users\<ユーザー>\Music\sample-a.MP3" -m small -o <出力先>
```

## 4. 精度（幻覚ループの量）

### 指標について

行単位の重複率だけでは、**1行の中で同じ表現が繰り返される**ケースを見逃す（cpp は1行が長い）。
そこで gzip 圧縮比を主指標にした。これは whisper 自身が繰り返し検出に使う
`compression_ratio_threshold` と同じ考え方で、**同じ表現の反復が多いほど圧縮比が高くなる**。

日本語の自然な会話文はおおむね 2.5〜3.5 に収まる。

### 結果

| 指標 | faster (int8) | cpp（`-mc 0`） | cpp（素の既定） |
| --- | --- | --- | --- |
| 文字数 | 10,982 | 11,198 | 12,192 |
| 行数 | 754 | 426 | 591 |
| **gzip 圧縮比**（低いほど自然） | **3.18** | **3.21** | **4.54** |
| 行内の繰り返し | 0 行 | 1 行（172文字 = 全体の 1.5%） | 1 行 |
| 行単位の重複率 | 6.9% | 6.1% | 38.1% |
| 最多の重複行 | 「はい。」14回（自然な相槌） | 「クリームチョコレートを使用されています。」9回 | 「(小麦粉を少しずつ入れてください。)」**208回** |

**`-mc 0` によって cpp は faster と同等（3.21 対 3.18）になった。**
素の既定（4.54）は、文字数だけ多くて中身が繰り返しで水増しされている状態。

### part ごとの出力サイズ（バイト）

| | part_000 | part_001 | part_002 | part_003 |
| --- | --- | --- | --- | --- |
| faster | 3,202 | 10,089 | 10,504 | 5,643 |
| cpp（`-mc 0`） | 4,749 | 10,730 | 10,721 | 5,039 |
| cpp（素の既定） | 12,188 | 10,199 | 10,095 | **403** |

素の既定は part_003 が **403 バイト**しかない（≒ 4.5分ぶんをほぼ取りこぼした）。
一方 part_000 は 12,188 バイトと多いが、これは繰り返しによる水増し。

### 実際の出力

**part_003（270秒）— 素の既定は崩壊、`-mc 0` で回復**

```
[faster ]  ま、さっき取り返されていたんですけど、/ ドッグは5御休なのです。/
           どうこまれてきるかというのがあると思います。/ ...（5,643 バイト）

[cpp -mc0] ずっと、他の、まあさっき振り返されてたんですけど、他559なので、
           どこまでできるかっていうのが、今、そこは、あります。/ そうですね。/ ...（5,039 バイト）

[cpp 既定 ] ずっと、他の、まあさっき振り返されてたんですけど... /
           (音楽) / (音楽) / (音楽) / (音楽) ...（403 バイト）
```

**part_000 冒頭 — cpp は `-mc 0` でも1箇所だけループが残る**

```
[faster ]  【音楽】/ 優先でやるのもかりかなと思ってます / アプリプス? /
           アプリプステレガーとみんなで始まるので / っていうぐらいかなと思ってますが / ...

[cpp -mc0] [音楽] / (中村)優先でやるのも仮かなと思ってます / (大平)うん / (大平)アフェプト? /
           (中村)アフェプトでやるのも アフェプトでやるのも アフェプトでやるのも ...（172文字ループ）
```

### エンジンごとの傾向

- **faster**: 繰り返しゼロ。句読点は少なめで、短い行に分かれる（754行）。
- **cpp**: 句読点が丁寧に付き、1行が長い（426行）。ただし
  - `(中村)` `(大平)` のような**話者ラベルを勝手に付ける**ことがある（話者分離は無効なのでモデルの推測）。
  - `クリームチョコレートを使用されています。` のような**文脈外の語**を混ぜることがある。
  - 冒頭など一部でループが残る（全体の 1.5%）。

どちらも固有名詞・専門用語の誤変換は同程度に発生する（`small` モデルの限界）。

## 5. チューニングの経緯（1変数ずつ検証）

崩れが最も激しかった part_003（270秒）で、パラメータを1つずつ足して効果を測った。

| 段階 | 重複率 | 所要時間 | 出力 | 判断 |
| --- | --- | --- | --- | --- |
| ベースライン（素の既定） | 78.9% | 79.6秒 | 403 バイト | 「(音楽)」16回連続で実質崩壊 |
| **(1) `-mc 0` を追加** | **4.1%** | 117.2秒 | **5,039 バイト**（12.5倍） | **十分改善。これを採用** |
| (2) `--suppress-nst` を追加 | 未実施 | — | — | (1) で足りたため不要 |
| (3) VAD を有効化 | 未実施 | — | — | 同上（VAD モデルの別途入手も不要） |

`-mc 0` は「直前のテキストを文脈として引き継がない」設定。whisper.cpp には faster のような
繰り返し検出が無いため、**文脈の引き継ぎを切ることが実質的な対策**になる。

## 6. 結論と、実装への反映

### 判断

- **Windows は faster(int8) を継続**。速度・品質とも僅差で勝り、幻覚もゼロだった。
- **Mac / Ubuntu は cpp で実用水準**。Python 不要という当初の目的を、品質をほぼ落とさずに達成できる。
- **cpp を使うなら `-mc 0` は必須**。素の既定では「同じ文が208回」レベルで崩れ、要約にも使えない。

### この計測を受けて入れた変更

| 変更 | 内容 |
| --- | --- |
| `transcribe.whisper.cpp.max-context` | **既定 0**（`-mc 0` を渡す）。負値なら `-mc` を渡さず whisper-cli の既定に任せる |
| README | 「どのエンジンを選ぶか（実測）」の比較表と `max-context` の説明を追記 |

### 未計測・今後

- **openai エンジン**: 参考のため実行したが、所要時間が長い（30〜60分見込み）ため中断した。
- **cpp に残る 1.5% のループ**: `--suppress-nst` や VAD で消せる可能性がある。実運用で気になったら試す。
- **量子化モデル**: `--model small-q5_1`（181MB）で速度・品質がどう変わるか。モデル置き場に
  `ggml-small-q5_1.bin` を置けば設定変更なしで比較できる。
- **Mac（Intel）での再計測**: 本レポートと同じ手順で計測すれば、そのまま比較できる。
  Metal が効かないため、Windows と同程度かやや遅い想定。

## 7. 計測の再現方法

```powershell
# 1. 出力フォルダを分けて（または --force を付けて）各エンジンを実行する
#    ※冪等性があるため、同じフォルダに再実行するとスキップされて計測にならない

# 2. 所要時間はアプリのログに出る
#    [4/4] 文字起こし完了: 4件 / 合計 13分37秒 (engine=cpp, model=small)

# 3. 圧縮比（幻覚の量）は _all.txt から算出する
$bytes = [System.IO.File]::ReadAllBytes("<出力先>\sample-a_all.txt")
$ms = New-Object System.IO.MemoryStream
$gz = New-Object System.IO.Compression.GZipStream($ms, [System.IO.Compression.CompressionLevel]::Optimal)
$gz.Write($bytes, 0, $bytes.Length); $gz.Close()
"圧縮比: {0}" -f [math]::Round($bytes.Length / $ms.ToArray().Length, 2)
```

## 追記: 4 番目のエンジン — FFM（`transcribe-ffm`、2026-09-08）

whisper.cpp を**外部バイナリではなく JVM 内から FFM（Panama）で直接呼ぶ**経路を追加した。
ライブラリは [whisper-ffm](https://github.com/juju351nicu/whisper-ffm)（`jp.clip:whisper-ffm`）で、
whisper.cpp v1.9.3 のネイティブを jar に同梱している。Windows は追加インストールが要らない。
コマンドは `transcribe-ffm` / `transcribe-ffm-all`、設定は `transcribe.ffm.*`（`transcribe.whisper.cpp.*` とは別）。

### 速度（Windows / i5-1335U / CPU / small）

| 音声 | エンジン | 処理時間 | RTF |
|---|---|---|---|
| 42.6 分 × 6 本（計 3 時間 20 分） | faster (int8) | 約 2 時間 | 0.56〜0.63 |
| 同上 | FFM（VAD on） | 約 35 分 | 0.17〜0.19 |
| 31 分 | FFM（VAD off = 既定） | 8 分 32 秒 | 0.28 |
| 12 分 38 秒 | FFM（VAD off = 既定） | 257 秒 | 0.34 |

この PC では **FFM が faster の 2.3〜3.5 倍速い**。VAD を on にすると更に速いが、下記の理由で既定は off。

### VAD は既定 off（`transcribe.ffm.vad=false`）

whisper.cpp の VAD は発話区間を繋ぎ合わせてから認識するため、繋ぎ目付近の文をまるごと落とす。
31 分の会議で比較すると VAD on 4,993 文字・4 分、VAD off 7,195 文字・8 分 32 秒、faster 7,557 文字・20 分 31 秒。
余白（`vad-speech-pad-ms` 30 → 300 → 500）やしきい値（0.5 → 0.35）を振っても 5,247 / 5,183 文字までしか戻らず、
落ちているのは短い発話ではなく文まるごとだった。議事録用途では網羅性を優先して off。

### デコーダの既定はライブラリ（= whisper.cpp）と意図的に違える

| 設定 | このアプリ | whisper.cpp | 実測での理由 |
|---|---|---|---|
| `best-of` | -1 | 5 | 5 にしても処理時間は同じ（244 対 257 秒）、文字数はむしろ 2.6% 減、繰り返しの差も無し |
| `temperature-increment` | 0.4 | 0.2 | 同上 |
| `beam-size` | 2 | 5 | 速度優先（greedy 既定なので通常は効かない） |
| `suppress-non-speech-tokens` | true | false | 記号の注記が邪魔。ただし whisper.cpp の抑制対象は固定の記号リストのみで `【】` は含まれない |

### 繰り返しループ: `-mc 0` に相当する手が使えない

whisper-cli 側は `-mc 0`（`n_max_text_ctx=0`）で文脈の引き継ぎを切っているが、FFM 側で同じ値にすると
**初期プロンプト（参加者名のヒント）も無効になる**。whisper.cpp のプロンプト構築が
`if (n_max_text_ctx > 0)` の中にあるため。参加者名の効果は実測で確認できている（ある姓が 4 → 7 回、
別の姓が 0 → 5 回、正しく出るようになった）ので、これを捨てる選択は取らなかった。

代わりに `carry-initial-prompt=true`（初期プロンプトを毎ウィンドウ前置）を試したが**採用しなかった**。

| 条件（12 分 38 秒 / small / VAD off / プロンプトあり） | 文字数 | 行数 | 時間 | 3 行以上の繰り返し | 姓A / 姓B |
|---|---|---|---|---|---|
| 既定 | 3,542 | 93 | 257 秒 | 0 行 | 2 / 0 |
| `carry-initial-prompt=true` | 4,713 | 166 | 271 秒 | **42 行** | **7 / 1** |

固有名詞には効いたが、**初期プロンプト自身が出力に漏れて同じ 1 行が 42 行連続**した。
プロンプトの影響力を上げる機構であって、上げすぎると復唱を招く。繰り返しループの対策には使えない。

**未解決**: FFM 側の繰り返しループへの万能な対策はまだ無い。VAD off の 31 分の会議では
幻聴の 1 行が 8 行続く例が出ている（全体に対しては小さい）。候補は、区間ごとに `whisper_full` を
分けて呼ぶ（whisper.cpp 内蔵 VAD のように繋ぎ合わせない）、出力側で繰り返しを検出して該当区間だけ
温度を変えて再処理する、など。いずれも未実装。

ただし後述の `sample-d` で、**無音が多い録音では VAD on がループを完全に止める**ことが分かった。

### 追記: 無音の多い録音でループが 10 分ぶんを飲み込んだ（`sample-d`、2026-09-08）

16 分 44 秒の会議（small / 既定 / 初期プロンプトあり / `--segment-time 600` で 3 part）。
2 番目・3 番目の part は正常だったが、**1 番目の part（10 分）が幻聴の 1 行だけで埋まり、
会話が 1 文も残らなかった。**

| part_000（同じ 10 分を条件だけ変えて 3 回） | 文字数 | 非空行 | 最長の連続同一行 | 処理時間 | RTF |
|---|---|---|---|---|---|
| VAD off / プロンプトあり（既定） | 605 | 55 | **55**（会話 0 文） | 約 180 秒 | — |
| **VAD on / プロンプトあり** | **2,296** | **149** | **2** | **104 秒** | **0.17** |
| VAD off / プロンプトなし | 1,379 | 67 | **12** | 166 秒 | 0.28 |

**初期プロンプトは原因ではない。** 外してもループした（55 → 12 行に減っただけ）。

原因は part_000 の音の性質だった。`ffmpeg` の `silencedetect=noise=-40dB:d=1.0` で測ると、
このパートだけ非発話区間が突出している。

| | 全長 | 無音（−40dB / 1 秒以上） | 発話 | 無音区間の数 |
|---|---|---|---|---|
| **part_000** | 600 秒 | **139 秒（23.2%）** | 461 秒 | **49** |
| part_001 | 600 秒 | 42 秒（7.0%） | 558 秒 | 25 |
| part_002 | 405 秒 | 28 秒（6.8%） | 377 秒 | 15 |

無音の割合が 3 倍、区間の数が 2 倍。非発話区間で whisper が幻聴を起こし、
`n_max_text_ctx = 16384` の引き継ぎがそれを次のウィンドウへ運んで固定する、という筋書きと一貫する。
音量そのものは 3 パートとも同水準（`mean_volume` −26.0 / −23.9 / −24.1 dB）で、
「録音が小さすぎた」わけではない。

**VAD の損得は録音の性質で逆転する。** 上の「VAD on は文字数が 3 割減る」は発話が途切れない
録音での測定値だった。`sample-d` の part_000 では、VAD on の 2,296 文字は実発話 461 秒に対して
妥当な量で、取りこぼしではない（同じ 10 分尺で発話 558 秒の part_001 が 3,376 文字）。

**運用**: 既定は `vad=false` のままにしてある。1 録音の結果で既定を変えるべきではないため。
会議前の待ち時間が入っている録音や、沈黙の長い少人数の会議では `--vad` を手で付ける。
数録音ぶん溜まったら、既定を on にするか、無音率を測って自動で切り替えるかを判断する。

### 追記: 無音率と崩壊の対応（2 録音 5 part、2026-09-09）

2 本目（`sample-e`、18 分 58 秒、small / 既定 / VAD off）は崩壊しなかった。無音率が低い。

| part | 尺 | 無音率（−40dB / 1 秒以上） | 最長の連続同一行 | 文字数 ÷ 音声秒 | 結果 |
|---|---|---|---|---|---|
| `sample-d` part_000 | 10 分 | **23.2%** | **55** | **1.01** | 崩壊 |
| `sample-d` part_001 | 10 分 | 7.0% | 2 | 5.63 | 正常 |
| `sample-d` part_002 | 6.7 分 | 6.8% | 2 | 5.16 | 正常 |
| `sample-e` part_000 | 10 分 | 3.8% | 2 | 4.19 | 正常 |
| `sample-e` part_001 | 8 分 | 5.5% | 1 | 4.70 | 正常 |

無音率 7% 以下は 4/4 で正常、23% で崩壊。この時点では「無音率が予測指標になりそう」と考えたが、
**次の節でこの読みは否定された。** 崩壊例 1 件からの一般化が早すぎた。

### 訂正: 無音率は条件ではない（3 録音 8 part、2026-09-09）

さらに 2 録音（`sample-f` / `sample-g`、各 16〜18 分、small / 既定 / VAD off）を流したところ、
**無音率 0.0% の part で 67 行連続と 16 行連続が出た。** 上の「無音率が予測指標になりそう」は誤り。
無音の多さは一因ではあっても、崩壊の条件ではない。

| part | 尺 | 無音率 | 最長の連続同一行 | 文字数 ÷ 音声秒 | 判定 |
|---|---|---|---|---|---|
| `sample-d` part_000 | 600 秒 | 23.2% | **55** | **1.01** | 崩壊 |
| `sample-d` part_001 | 600 秒 | 7.0% | 2 | 5.63 | 正常 |
| `sample-d` part_002 | 405 秒 | 6.8% | 2 | 5.16 | 正常 |
| `sample-f` part_000 | 600 秒 | 6.5% | 3 | 3.39 | 正常（3 行は普通の発話文） |
| **`sample-f` part_001** | 383 秒 | **0.0%** | **67** | 5.07 | 崩壊 |
| **`sample-g` part_000** | 600 秒 | **0.0%** | **16** | 3.63 | 崩壊 |
| `sample-g` part_001 | 323 秒 | 0.0% | 2 | 4.15 | 正常 |
| `sample-e` part_000 | 600 秒 | 3.8% | 2 | 4.19 | 正常 |
| `sample-e` part_001 | 478 秒 | 5.5% | 1 | 4.70 | 正常 |

繰り返される内容には 2 種類ある。

- **完全な幻聴** — 料理の手順のような、話されていない定型文。`sample-g` の 16 行は
  「私は、私のビデオを紹介します。」で、31 分の録音で 8 行続いたのと**同一の文**だった。
  whisper が非発話区間で出す決まり文句が固定化したもの。
- **実発話のロックイン** — `sample-f` の 67 行は、実際に話された 1 文がそのまま繰り返された形。
  幻聴ではなく、引き継ぎプロンプトによる復唱と見える。

**文字数の指標だけでは崩壊を捕まえられない。** `sample-f` part_001 は 67 行連続しているのに
5.07 文字/秒で、正常な part（3.39〜5.63）の範囲に収まっていた。繰り返しが短い 1 文なので
総文字数が減らないため。**連続同一行の指標が必須**である。

**しきい値を 3 → 5 に変えた。** `sample-f` part_000 の「3 行連続」は普通の発話文の重複で崩壊ではなく、
3 では誤検知した。崩壊側の最小は 16 なので、3 と 16 の間の 5 に置いて両側に余裕を持たせた。

**無音率 0% の part をどう直すかは未解決。** `--vad` が効いたのは無音の多い `sample-d` の 1 例だけで、
無音の無い part に効く保証はない。この 2 件は再処理しても同じ結果（16 行）が再現するので、
デコーダ側の条件を振る A/B が次の課題になる。

### 崩壊の検知を実装した（警告のみ）

上の実測から、`TranscriptQualityCheck` が part を書き出すたびに次を数えて WARN を出すようにした。

| 指標 | 既定 | 崩壊 part の値 | 崩壊していない part の値 |
|---|---|---|---|
| 同一行の連続回数 | **5** 行以上で警告 | 16 / 55 / 67 | 1〜3 |
| 音声 1 秒あたりの文字数 | 2.5 未満で警告 | 1.01（67 行の part は 5.07 で捕まらない） | 3.39〜5.63 |
| 結果が空 | 常に警告 | — | — |

実データでの発火も確認した。`sample-g` part_000 を流し直すと
`要確認: 同じ行が 16 行連続しています（「…」）` が出て、行数も前回と同一に再現した。

`.txt` は必ず書き出し、例外にもしない。**対処（`--vad` への切り替え）は自動化していない。**
VAD は発話が途切れない録音では文字数を 3 割落とすため、崩壊例が少ないうちに挙動を変えると
正常な録音を壊す方に転ぶ。判断は人に残す。

入れなかった指標とその理由: 非連続の繰り返し（「はい。」等が普通に 6〜7 回出るので誤検知の線引きが
決まらない）、末尾の欠落、part 数の検算（いずれも観測例がゼロ）。

### まとめ: VAD は両刃で、予測はできない（6 part の A/B、2026-09-09）

同一音声・同一設定で `vad` だけを振った 6 パート。`c/s` は音声 1 秒あたりの文字数。

| part | 平均音量 | 無音率 | VAD off | VAD on | 差 |
|---|---|---|---|---|---|
| `sample-d` part_000 | −26.0 dB | 23.2% | **崩壊** 55 行連続 / 1.01 c/s | 正常 3.83 c/s | **VAD が直した** |
| `sample-h` part_000 | −24.9 dB | 7.3% | **崩壊** 14 行連続 / 0.72 c/s | 正常 3.91 c/s | **VAD が直した** |
| `sample-h` part_001 | −23.3 dB | 0.2% | **崩壊** 60 行連続 / 5.87 c/s | 正常 6.00 c/s | **VAD が直した**（文字数は +2%） |
| `sample-h` part_002 | −23.9 dB | 0.0% | 正常 5.12 c/s | 正常 5.10 c/s | −0.4% |
| `sample-e` part_001 | −28.5 dB | 5.5% | 正常 4.58 c/s | 正常 4.29 c/s | −6.5% |
| `sample-e` part_000 | −29.9 dB | 3.8% | 正常 4.02 c/s | **崩壊** 0.67 c/s | **VAD が壊した（−83.2%）** |

**音量とは相関する。** −23〜−26 dB では VAD on が無害か有益、−28.5 dB で −6.5%、−29.9 dB で −83%。
ただし**しきい値はレバーではなかった。** `vad-threshold` を 0.5 → 0.6 ではなく 0.2 に下げても
`sample-e` part_000 は 404 → 621 文字（VAD off は 2,410 文字）で、−74% のままだった。
「音が小さいと確度がしきい値を超えず発話が捨てられる」という機構の説明は成り立たない。
原因は whisper.cpp の VAD の区間切り出しか結合の側にあると思われるが、未調査。

**予測はできない。** 無音率（23.2% で崩壊、0.2% でも崩壊、3.8% では VAD が壊した）、
平均音量（相関はあるが境界が引けない）、`vad-threshold`（効かない）のいずれでも判定できなかった。

#### したがって運用手順で回す

1. 既定（`vad=false`）で流す
2. 警告が出た part の `.txt` を消して `--vad` で流し直す
3. それでも警告が出るなら VAD off の結果に戻す

**既定を `vad=true` にはしない。** 崩壊の修正に 3 勝しているが、静かな録音では自分が −83% の
崩壊を作る。既定にできる性質のものではない。

**この手順は品質チェックが両方向を見ているから成立する。** VAD off の崩壊は「同一行の連続」で、
VAD on の崩壊は「音声 1 秒あたりの文字数」で捕まる（VAD on の結果は最長連続 1 行で、
繰り返しの観点では完璧に見える）。2 つ目の指標を入れたのはここで効いた。

#### 追記: 誤検知 1 件と、手で詰める方が良い場合（`sample-i`、2026-09-10）

18 分 41 秒の会議（small / 既定 / 2 part）。両 part が警告を出したが、中身は別だった。

| part | VAD off | VAD on | 最良 |
|---|---|---|---|
| part_000（600 秒） | 20 行連続 / 3,434 文字 / 5.72 c/s | 1 行 / 1,692 文字 / 2.82 c/s（**−51%**） | **VAD off から 20 行を 1 行に詰める → 2,864 文字** |
| part_001（561 秒） | 5 行連続 / 3,193 文字 / 5.69 c/s | 2 行 / 3,445 文字 / 6.14 c/s（**+7.9%**） | VAD on |

**連続同一行が 1 ブロックなら、手で詰めるのが最善のことがある。** part_000 は `--vad` で繰り返しは
消えたが実内容も 4 割削られた。20 行の繰り返しが占めていたのは約 570 文字ぶんなので、
VAD off から詰めれば 2,864 文字が残る。`--vad` の結果を採る前に文字数を必ず見比べること。

**part_001 の「5 行連続」は誤検知だった。** 繰り返された行は「はい。」で、自然な相槌である。
既定のしきい値 5 では相槌を拾ってしまう。

そこで**短い行の連続を数えない**条件を足した（`repetition-min-line-length`、既定 8）。
回数を 5 → 6 に上げる案より長さで切る方を選んだ理由は、実測の分かれ方が長さで説明できるため。

| | 繰り返された行 | 文字数 |
|---|---|---|
| 崩壊 | 「私は、私のビデオを紹介します。」 | 15 |
| 崩壊 | 「バランスの通りに見えるほど良いです。」 | 18 |
| 崩壊 | 「1,787億を作っていなかったので、」 | 18 |
| 崩壊 | 「クリームの発酵が必要なのですが、…最高です。」 | 30 |
| **誤検知** | 「はい。」 | **3** |

崩壊時の行は幻聴も実発話の復唱も文の形をしていて 15 文字以上、相槌は 3 文字。8 はその間に取った。
「長い文が 5 行続くのは崩壊、相槌が 6 行続くのは自然」という区別をそのまま条件にできる。

#### 却下・否定された仮説（同じ道を通らないために）

| 仮説 | 結果 |
|---|---|
| 無音率が崩壊の予測指標になる | **否定。** 無音率 0.0〜0.2% でも 60〜67 行連続が起きる |
| 初期プロンプトが崩壊の原因 | **否定。** プロンプトを外してもループした（55 → 12 行に減っただけ） |
| VAD on は常に文字数を 3 割落とす | **否定。** −0.4% の part もあり、崩壊 part では逆に +2% になった |
| VAD on は無音の無い part には効かない | **否定。** 無音率 0.2% の part で 60 行連続が 1 行になった |
| 音が小さいと VAD のしきい値を超えないので落ちる | **否定。** しきい値を 0.2 に下げても −74% のまま |
| `carry_initial_prompt=true` が繰り返しに効く | **否定。** プロンプト自身が 42 行繰り返された（前述） |
| `best_of` を上げると繰り返しから抜けやすい | **否定。** 処理時間は同じで文字数はむしろ減った（前述） |

いずれも**崩壊例が 1〜2 件の段階で一般化したのが原因**だった。既定値やコードを動かす前に、
同一音声での A/B を複数パート分そろえること。
